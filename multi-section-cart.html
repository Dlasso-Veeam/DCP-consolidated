A cart that holds pending restores from several workloads

Today a cart is a selection inside one workload, and switching workload clears it. Here the cart can hold one pending restore per workload. Every pending restore keeps its own restore wizard, exactly as today, with nothing from another workload in it. The cart is only the list of what is waiting, and a way into each wizard, one at a time.

1

What the cart looks like

The chip keeps telling you what is in the cart you are working on. When other carts exist, a cart button with a count badge next to it lists them.

Behaviour

  • The chip is unchanged: "2 users selected ×" always describes the cart for the workload you are viewing, whether or not other carts exist.
  • With more than one cart a cart button with a count badge sits beside the chip. The Restore button stays where it is and always restores the selected cart.
  • The tray lists every cart: workload, what is in it, the restore point it will use. The selected cart is marked Selected. The others have Select, and every cart has a remove control.
  • Select makes that cart the current one: the workload picker, the table and the chip all switch to it. Then Restore starts its wizard.
  • After a restore is submitted, its row shows the session status and a link to it, and the other carts stay as they were.
  • There is no "restore everything" button and no combined wizard.

Why this shape

  • The tray never restores, because the Restore button already does. It only changes which cart that button acts on.
  • It reuses the filter-picker popover pattern already on the page.
2

How you get into a multi-section cart

Three ways in. Only the first changes how someone browses.

Notes

  • Browsing. Switching the workload picker used to clear the cart. It now keeps the cart and starts a new one for the workload you open. A toast says what was kept, and the cart pill appears.
  • From a finding. Restore all on a finding that spans workloads puts one cart per workload in the list, with the recommended restore points, and opens Protected Data with the tray open and a tag back to the finding. Select one, then Restore, and compare or change it like any other restore.
  • Deep link. The existing restore link carries one workload. It would accept several, one pending restore per workload, plus the point for each.

Decision

  • Should anyone be able to build a mixed cart by browsing, or only findings, at least at first? Allowing both is the smaller rule. Findings then become the first source of mixed carts, not the only one.
3

Restoring one cart at a time

Select a cart, then Restore. The wizard is the one that exists today and only ever contains its own workload.

Behaviour

  • Select on a tray row switches the workload picker, the table and the chip to that cart. The Restore button now acts on it.
  • Restore opens that workload's wizard on the step it was left at. From a finding it opens on Summary, because the finding filled in the earlier steps.
  • Submitting starts that session and returns to the page, where the cart's row shows its status and the other carts are still waiting.
  • The order is up to the person. If the system needs one workload to restore before another, it holds the later session and the row says so in its status.

Closing a wizard

  • Closing without submitting leaves the cart as it was, with its choices intact.

What changes from today

5

On the finding: Restore points tab and Overview step 3

The finding no longer restores anything itself. It compares, queues pending restores in the cart, and mirrors what the cart and the sessions say. Step through what happens.

Restore points tab

  • Each workload block is in one of four states: not in the cart (Compare in Protected Data, Add to cart, Restore), in your cart (Open in Protected Data, remove), submitted (status and View session), or failed (Retry).
  • Compare in Protected Data is unchanged. Choosing a different restore point there updates the pending restore, and the block shows "Chosen in Protected Data".
  • The tab header has one button that follows the state: Add all to cart (3), Add remaining to cart (1), Open cart (3 pending), then View in Activity.
  • Open in Protected Data opens that cart there, already selected, so Restore is one click away. Restore on a block adds it to the cart and opens its wizard straight away.

Overview, step 3

  • A read-only mirror: each workload with the account, what comes back, the restore point and the options, plus the same state chip as its block.
  • One button, the same one as the tab header, and a status line such as "3 in your cart · 1 of 3 restored".
  • When all three have succeeded, the step offers to move the finding to Resolved - Remediated. It only asks.

One source of truth

  • The finding stores nothing about the restore. Every state comes from the cart and the sessions. Add or submit from Protected Data and both views update. Remove from the cart and the block goes back to "not in the cart".
  • The History records "Added to cart", the session start and the result, so the trail survives.
